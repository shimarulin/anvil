# Anvil — Architecture Decision Records

Architectural decisions made during Anvil design, with context, alternatives
considered, and rationale.

## Format

Each decision follows a lightweight ADR format:

- **ID**: Sequential identifier
- **Status**: Accepted / Superseded / Deprecated
- **Context**: Why the decision was needed
- **Decision**: What was decided
- **Alternatives**: What else was considered
- **Consequences**: What follows from this decision

## Decisions

### ADR-001
#### NVIM_APPNAME Isolation

**Status:** Accepted

**Context:** Users may have an existing Neovim configuration they don't want to
disrupt. Anvil needs to coexist with other configs on the same machine.

**Decision:** Use Neovim's built-in `NVIM_APPNAME` mechanism (available since
0.9) to run Anvil in a completely isolated environment.

```bash
NVIM_APPNAME=anvil nvim    # uses ~/.config/anvil/
nvim                        # uses ~/.config/nvim/ (untouched)
```

**Alternatives:**
- Separate Neovim binary — impractical
- Docker container — too heavy for an editor
- Manual XDG path overrides — fragile

**Consequences:**
- Clean separation between configurations
- Mason packages, plugin data, sessions are all isolated
- Alias `alias anvil='NVIM_APPNAME=anvil nvim'` provides convenient access
- Scripts must always set `NVIM_APPNAME` for headless operations

### ADR-002
#### Language-First Architecture

**Status:** Accepted

**Context:** Traditional Neovim configs scatter language support across multiple
files: LSP config here, formatter there, DAP somewhere else. Adding a new
language requires touching 5-10 files.

**Decision:** Each language is a self-contained pack — a single Lua table that
declares everything: LSP, treesitter, formatter, linter, DAP, test runner,
tasks, AI context, keymaps, and extra plugins.

**Alternatives:**
- AstroCommunity packs — not customizable enough, can't add AI context
- Per-plugin configuration — doesn't scale
- Language-specific plugin collections (e.g., go.nvim) — vendor lock-in

**Consequences:**
- Consistency: every language has the same structure
- Discoverability: look at one file to understand everything about a language
- The lang engine becomes a critical component
- Some languages need escape hatches (see ADR-004)

---

### ADR-003
#### Single-File Language Packs

**Status:** Accepted

**Context:** The language pack could be a directory with multiple files or a
single file returning a table.

**Decision:** Single file per language. The `AnvilLangPack` type contract is
comprehensive but flat.

**Alternatives:**
- Directory per language — more files to navigate
- Separate registration files — loses the "one place" benefit

**Consequences:**
- Files can get long (150-300 lines for complex languages)
- But everything is in one place
- Easy to copy `_template.lua` and fill in

---

### ADR-004
#### Lang Engine Flags: managed_by_plugin, managed_by_lsp

**Status:** Accepted

**Context:** Most languages follow the standard path: LSP via lspconfig,
formatter via conform. But some languages have specialized plugins that manage
these components themselves (e.g., rustaceanvim manages rust-analyzer directly).

**Decision:** Two boolean flags in the lang pack:

```lua
lsp = {
  server = "rust_analyzer",
  managed_by_plugin = true,  -- skip lspconfig registration
},
formatter = {
  tool = "rustfmt",
  managed_by_lsp = true,     -- skip conform registration
},
```

**Consequences:**
- The lang engine remains the single source of truth
- Specialized plugins get full control where needed
- Mason install list is always complete

---

### ADR-005
#### Dual LSP Support (extra_servers)

**Status:** Accepted

**Context:** Python benefits from running two LSP servers simultaneously:
basedpyright for type checking and ruff for lint code actions.

**Decision:** Add `extra_servers` field to the LSP section:

```lua
lsp = {
  server = "basedpyright",
  extra_servers = {
    { server = "ruff", on_attach = function(client) ... end },
  },
},
```

**Consequences:**
- Capability conflicts must be resolved in `on_attach`
- Pattern is reusable for other languages

---

### ADR-006
#### Formatter Chains

**Status:** Accepted

**Context:** Go requires two formatters in sequence: goimports then gofumpt.

**Decision:** Add `formatter.chain` field:

```lua
formatter = {
  tool = "goimports",
  chain = { "goimports", "gofumpt" },
},
```

**Consequences:**
- `formatter.tool` is the primary (for mason install)
- `formatter.chain` overrides the conform configuration
- Order matters

---

### ADR-007
#### conform.nvim + nvim-lint, Not null-ls

**Status:** Accepted

**Context:** null-ls (now none-ls) pretends external tools are LSP servers,
which creates complexity.

**Decision:** Use purpose-built tools: conform.nvim for formatting, nvim-lint
for linting.

**Consequences:**
- Two plugins instead of one, but each is simpler
- Format-on-save handled by conform, not LSP
- Some LSP servers need their formatting disabled

---

### ADR-008
#### CodeCompanion as Primary AI, Not Avante

**Status:** Accepted

**Context:** Multiple Neovim AI chat plugins exist. The AI ecosystem needs a
primary interface supporting: OpenAI-compatible API, tool use, MCP, slash
commands, customizable prompts, inline code actions.

**Decision:** CodeCompanion as the primary AI interface.

**Rationale:**
- Fully open source, active development
- OpenAI-compatible adapter works with any provider
- Rich slash command and variable system
- MCP integration via mcphub.nvim
- Customizable prompt library
- Inline code actions with diff view

**Consequences:**
- All AI chat workflows go through CodeCompanion
- Avante could be added as optional alternative later

---

### ADR-009
#### Unified AI Provider Configuration

**Status:** Accepted

**Context:** Multiple AI tools all need API endpoints and keys.

**Decision:** Single provider module (`anvil/ai/providers.lua`) reads from
environment variables and `.env` files. All AI tools reference this module.

Four provider tiers: main, fast, planner, local.

**Consequences:**
- One place to change API keys or switch providers
- `.env` file is gitignored (security)
- External tools receive credentials via environment variables

---

### ADR-010
#### External AI Tools via toggleterm

**Status:** Accepted

**Context:** Heavy AI tasks benefit from specialized external tools: aider,
opencode.

**Decision:** Launch external AI tools as toggleterm terminals within Neovim.
Each tool gets a dedicated Terminal instance with pre-configured environment
variables.

**Consequences:**
- External tools run inside Neovim's UI
- Context can be passed from editor to external tool
- File changes are picked up by Neovim (autoread)

---

### ADR-011
#### MCP as Extensibility Standard

**Status:** Accepted

**Context:** AI agents need access to external resources: databases, APIs, file
systems, web search.

**Decision:** Use Model Context Protocol (MCP) as the standard for connecting
AI agents to external tools. MCP servers managed by mcphub.nvim.

**Consequences:**
- New capabilities = install new MCP server (no code changes)
- Configuration in `~/.config/anvil/mcp-servers.json`

---

### ADR-012
#### rustaceanvim, Not rust-tools.nvim

**Status:** Accepted

**Context:** rust-tools.nvim is deprecated. rustaceanvim is its successor.

**Decision:** Use rustaceanvim v5. It manages rust-analyzer directly (not
lspconfig), hence `managed_by_plugin = true`.

**Consequences:**
- Configuration via `vim.g.rustaceanvim`
- The lang engine must not register rust_analyzer in lspconfig

### ADR-023
#### NvChad as Base Framework

**Status:** Accepted

**Context:** Anvil needs a base framework to provide plugin management, theme
system, and basic UI chrome. Options: AstroNvim v4, NvChad v2.5, standalone
lazy.nvim, kickstart.nvim.

**Decision:** NvChad as the base framework for the initial implementation.

**Rationale:**
- **Minimal core** — thin wrapper over lazy.nvim + base46 + ui. Less "magic",
  fewer hidden conventions. Anvil gets more control.
- **Imperative model** — `vim.keymap.set`, `vim.api.nvim_create_autocmd`,
  `lspconfig[server].setup()` — standard Neovim API. Anvil's language engine
  can call them directly without adapting to a declarative format.
- **No abstraction conflicts** — AstroNvim has AstroCore, AstroLSP, AstroUI
  which compete with Anvil's own layers. NvChad doesn't create such
  abstractions.
- **Cleaner Path A→C** — NvChad uses standard Neovim API, so editor layer code
  is framework-agnostic by default. Adding AstroNvim later means adapting
  agnostic code to a framework (easier) rather than extracting agnostic code
  from a framework (harder).
- **Fast startup** — base46 compile-time theme caching, ~30-40ms startup.

**Alternatives:**
- AstroNvim v4 — richer out-of-box experience, AstroCommunity packs, but
  abstraction conflicts with Anvil layers, harder Path C extraction.
- Standalone lazy.nvim — maximum control, but no theme system, no statusline,
  more boilerplate.
- kickstart.nvim — too minimal, no theme, no UI chrome.

**Consequences:**
- Must write LSP orchestrator (~200 LOC) — AstroLSP provided this for free
- No AstroCommunity fallback for language packs
- NvChad v2.5 → v3.0 migration risk
- All plugin specs in `lua/plugins/` are NvChad-idiomatic
- `chadrc.lua`, `options.lua`, `mappings.lua` follow NvChad conventions

### ADR-024
#### Framework-Agnostic Core (Path A→C Design)

**Status:** Accepted

**Context:** Anvil may need to support multiple frameworks in the future. The
core business logic should not be tied to any specific framework.

**Decision:** Structure the codebase from day one with an explicit boundary
between framework-agnostic code (~80%) and framework-specific code (~20%).

Framework-agnostic:
- `lua/anvil/core/*` — events, cache, logger, env
- `lua/anvil/lang/*` — language packs, registry, engine
- `lua/anvil/ai/*` — providers, context, agents, MCP
- `lua/anvil/config.lua` — user config schema

Framework-specific:
- `lua/anvil/ui/nvchad/*` — theme, statusline
- `lua/anvil/bridge/nvchad/*` — boot integration
- `lua/plugins/*` — LazySpec files

Boundary layer (Neovim API, not framework-specific):
- `lua/anvil/editor/*` — uses lspconfig, nvim-cmp, etc. directly
  with strategy points for future framework override

**Consequences:**
- Adding a second framework requires only: new `ui/<framework>/`, new
  `bridge/<framework>/`, new plugin specs, strategy overrides
- core/, lang/, ai/ remain untouched
- Estimated effort for Path C: ~2-3 weeks

### ADR-025
#### Strategy Points in Editor Layer

**Status:** Accepted

**Context:** The editor layer calls plugin APIs (lspconfig, nvim-dap, neotest)
directly. Different frameworks may need different integration patterns.

**Decision:** Key functions in the editor layer are exposed as overridable
module-level functions (strategy pattern):

```lua
-- editor/lsp.lua
M.register_server = function(server, opts)
  require("lspconfig")[server].setup(opts)
end
```

A framework bridge can override these before the lang engine runs:

```lua
-- bridge/astronvim/init.lua (future)
require("anvil.editor.lsp").register_server = function(server, opts)
  require("astrolsp").config[server] = opts
end
```

**Alternatives:**
- Abstract factory — over-engineering for 2-3 override points
- Dependency injection — Lua doesn't have a natural DI pattern
- Event-based — too indirect for synchronous setup

**Consequences:**
- Simple, explicit, easy to understand
- No performance overhead
- Each strategy point is documented in the editor module
- Bridge must override before `lang.setup()` runs

### ADR-026
#### Imperative Keymaps via vim.keymap.set

**Status:** Accepted

**Context:** AstroNvim uses declarative mapping tables in `astrocore.opts`.
NvChad uses `vim.keymap.set` in `mappings.lua`.

**Decision:** All Anvil keymaps use `vim.keymap.set` directly. This is the
standard Neovim API and works identically in any framework.

**Consequences:**
- Language pack keymaps (`pack.keys`) applied via `vim.keymap.set` with
  `{ buffer = bufnr }`
- Core keymaps in `core/keys.lua` use `vim.keymap.set`
- Plugin-specific keymaps in `lua/plugins/*.lua` use lazy.nvim `keys` field
- No need for declarative-to-imperative converters

---

### ADR-027
#### Direct lspconfig, Not Framework LSP Abstraction

**Status:** Accepted

**Context:** AstroNvim wraps lspconfig in AstroLSP. NvChad calls lspconfig
directly. Anvil needs a consistent approach.

**Decision:** Use `lspconfig[server].setup(opts)` directly in the editor layer.
Build capabilities, on_attach, and server settings from the lang engine.

**Rationale:**
- lspconfig is the standard — every framework ultimately calls it
- Direct calls mean no hidden behavior
- Strategy point (`register_server`) allows future framework override
- LSP orchestrator (~200 LOC) is a one-time cost

**Consequences:**
- Must build capabilities (cmp-nvim-lsp) manually
- Must manage on_attach chain manually
- Must handle formatting conflicts (disable server formatting when conform
  handles it)
- Full control over LSP lifecycle
