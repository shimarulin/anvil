# Anvil — Architecture Decision Records

Architectural decisions made during Anvil design, with context, alternatives considered, and rationale.

## Format

Each decision follows a lightweight ADR format:

- **ID**: Sequential identifier
- **Status**: Accepted / Superseded / Deprecated
- **Context**: Why the decision was needed
- **Decision**: What was decided
- **Alternatives**: What else was considered
- **Consequences**: What follows from this decision

## Decisions

### ADR-001

**NVIM_APPNAME Isolation**

**Status:** Accepted

**Context:** Users may have an existing Neovim configuration they don't want to disrupt. Anvil needs to coexist with other configs on the same machine.

**Decision:** Use Neovim's built-in `NVIM_APPNAME` mechanism (available since 0.9) to run Anvil in a completely isolated environment.

```bash
NVIM_APPNAME=anvil nvim   # uses ~/.config/anvil/
nvim                       # uses ~/.config/nvim/ (untouched)
```

**Alternatives:**
- Separate Neovim binary — impractical
- Docker container — too heavy for an editor
- Manual XDG path overrides — fragile

**Consequences:**
- Clean separation between configurations
- Mason packages, plugin data, sessions are all isolated
- Alias `alias anvil='NVIM_APPNAME=anvil nvim'` provides convenient access
- Scripts must always set NVIM_APPNAME for headless operations

### ADR-002

**Language-First Architecture**

**Status:** Accepted

**Context:** Traditional Neovim configs scatter language support across multiple files: LSP config here, formatter there, DAP somewhere else. Adding a new language requires touching 5-10 files.

**Decision:** Each language is a self-contained pack — a single Lua table that declares everything: LSP, treesitter, formatter, linter, DAP, test runner, tasks, AI context, keymaps, and extra plugins.

**Alternatives:**
- AstroCommunity packs — not customizable enough, can't add AI context
- Per-plugin configuration — doesn't scale
- Language-specific plugin collections (e.g., go.nvim) — vendor lock-in

**Consequences:**
- Consistency: every language has the same structure
- Discoverability: look at one file to understand everything about a language
- The lang engine becomes a critical component
- Some languages need escape hatches (see ADR-004)

### ADR-003

**Single-File Language Packs**

**Status:** Accepted

**Context:** The language pack could be a directory with multiple files or a single file returning a table.

**Decision:** Single file per language. The `AnvilLangPack` type contract is comprehensive but flat.

**Alternatives:**
- Directory per language — more files to navigate
- Separate registration files — loses the "one place" benefit

**Consequences:**
- Files can get long (150-300 lines for complex languages)
- But everything is in one place
- Easy to copy `_template.lua` and fill in

### ADR-004

**Lang Engine Flags: managed_by_plugin, managed_by_lsp**

**Status:** Accepted

**Context:** Most languages follow the standard path: LSP via lspconfig, formatter via conform. But some languages have specialized plugins that manage these components themselves (e.g., rustaceanvim manages rust-analyzer directly).

**Decision:** Two boolean flags in the lang pack:

```lua
lsp = {
  server = "rust_analyzer",
  managed_by_plugin = true,  -- skip lspconfig registration
},
formatter = {
  tool = "rustfmt",
  managed_by_lsp = true,     -- skip conform registration
},
```

**Consequences:**
- The lang engine remains the single source of truth
- Specialized plugins get full control where needed
- Mason install list is always complete

### ADR-005

**Dual LSP Support (extra_servers)**

**Status:** Accepted

**Context:** Python benefits from running two LSP servers simultaneously: basedpyright for type checking and ruff for lint code actions.

**Decision:** Add `extra_servers` field to the LSP section:

```lua
lsp = {
  server = "basedpyright",
  extra_servers = {
    { server = "ruff", on_attach = function(client) ... end },
  },
},
```

**Consequences:**
- Capability conflicts must be resolved in on_attach
- Pattern is reusable for other languages

### ADR-006

**Formatter Chains**

**Status:** Accepted

**Context:** Go requires two formatters in sequence: goimports then gofumpt.

**Decision:** Add `formatter.chain` field:

```lua
formatter = {
  tool = "goimports",
  chain = { "goimports", "gofumpt" },
},
```

**Consequences:**
- `formatter.tool` is the primary (for mason install)
- `formatter.chain` overrides the conform configuration
- Order matters

### ADR-007

**conform.nvim + nvim-lint, Not null-ls**

**Status:** Accepted

**Context:** null-ls (now none-ls) pretends external tools are LSP servers, which creates complexity.

**Decision:** Use purpose-built tools: conform.nvim for formatting, nvim-lint for linting.

**Consequences:**
- Two plugins instead of one, but each is simpler
- Format-on-save handled by conform, not LSP
- Some LSP servers need their formatting disabled

### ADR-008

**CodeCompanion as Primary AI, Not Avante**

**Status:** Accepted

**Context:** Multiple Neovim AI chat plugins exist. The AI ecosystem needs a primary interface supporting: OpenAI-compatible API, tool use, MCP, slash commands, customizable prompts, inline code actions.

**Decision:** CodeCompanion as the primary AI interface.

**Rationale:**
- Fully open source, active development
- OpenAI-compatible adapter works with any provider
- Rich slash command and variable system
- MCP integration via mcphub.nvim
- Customizable prompt library
- Inline code actions with diff view

**Consequences:**
- All AI chat workflows go through CodeCompanion
- Avante could be added as optional alternative later

### ADR-009

**Unified AI Provider Configuration**

**Status:** Superseded by ADR-028

**Context:** Multiple AI tools all need API endpoints and keys.

**Original Decision:** Single provider module reads from environment variables and .env files. Four provider tiers: main, fast, planner, local.

**Why superseded:** The flat 4-tier model was insufficient for real-world scenarios:
- Corporate environments need private providers
- Different projects need different provider configurations
- Users need to switch configurations without editing files or restarting
- Multiple providers with multiple models per provider
- Per-interaction-type model selection

See ADR-028 for the replacement.

### ADR-010

**External AI Tools via toggleterm**

**Status:** Accepted

**Context:** Heavy AI tasks benefit from specialized external tools: aider, opencode.

**Decision:** Launch external AI tools as toggleterm terminals within Neovim. Each tool gets a dedicated Terminal instance with pre-configured environment variables.

**Consequences:**
- External tools run inside Neovim's UI
- Context can be passed from editor to external tool
- File changes are picked up by Neovim (autoread)

### ADR-011

**MCP as Extensibility Standard**

**Status:** Accepted

**Context:** AI agents need access to external resources: databases, APIs, file systems, web search.

**Decision:** Use Model Context Protocol (MCP) as the standard for connecting AI agents to external tools. MCP servers managed by mcphub.nvim.

**Consequences:**
- New capabilities = install new MCP server (no code changes)
- Configuration in `~/.config/anvil/mcp-servers.json`

### ADR-012

**rustaceanvim, Not rust-tools.nvim**

**Status:** Accepted

**Context:** rust-tools.nvim is deprecated. rustaceanvim is its successor.

**Decision:** Use rustaceanvim v5. It manages rust-analyzer directly (not lspconfig), hence `managed_by_plugin = true`.

**Consequences:**
- Configuration via `vim.g.rustaceanvim`
- The lang engine must not register rust_analyzer in lspconfig

### ADR-013

**basedpyright + ruff Dual LSP for Python**

**Status:** Accepted

**Decision:** Run two LSP servers: basedpyright (types) + ruff (code actions). Capability conflicts resolved in on_attach.

### ADR-014

**typescript-tools.nvim for TypeScript**

**Status:** Accepted

**Decision:** Use typescript-tools.nvim for extra commands (organize imports, rename file, go to source definition).

**Critical rule:** Never run typescript-tools AND vtsls simultaneously.

### ADR-015

**ruff Replaces black + flake8 + isort**

**Status:** Accepted

**Decision:** Use ruff for formatting, linting, and import sorting in Python. 10-100x faster (written in Rust).

### ADR-016

**lazydev.nvim, Not neodev.nvim**

**Status:** Accepted

**Decision:** Use lazydev.nvim (by folke). neodev is in maintenance mode.

### ADR-017

**neotest-golang, Not neotest-go**

**Status:** Accepted

**Decision:** Use neotest-golang (fredrikaverpil) — better test discovery, testify support, DAP integration.

### ADR-018

**selene, Not luacheck**

**Status:** Accepted

**Decision:** Use selene — faster (Rust), better defaults, understands vim global.

### ADR-019

**Telescope as Universal Picker**

**Status:** Accepted

**Decision:** Telescope for all fuzzy-finding. Extensions: fzf, ui-select, file-browser, undo, live-grep-args.

### ADR-020

**Overseer for Task Management**

**Status:** Accepted

**Decision:** Use overseer.nvim for structured task management. Lang packs declare tasks, overseer runs them.

### ADR-021

**Layered Architecture with Event Bus**

**Status:** Accepted

**Decision:** Five-layer architecture with event bus for cross-layer communication. Boot sequence: Core → Lang → Editor → AI → UI.

### ADR-022

**minuet-ai for Inline Completion, Off by Default**

**Status:** Accepted

**Decision:** Use minuet-ai.nvim, disabled by default. Toggle with `<F2>`. Uses the "inline" slot.

### ADR-023

**NvChad as Base Framework**

**Status:** Accepted

**Context:** Anvil needs a base framework to provide plugin management, theme system, and basic UI chrome.

**Decision:** NvChad as the base framework for the initial implementation.

**Rationale:**
- Minimal core — thin wrapper over lazy.nvim + base46 + ui
- Imperative model — standard Neovim API
- No abstraction conflicts
- Cleaner Path A→C
- Fast startup — base46 compile-time theme caching

**Consequences:**
- Must write LSP orchestrator (~200 LOC)
- No AstroCommunity fallback for language packs
- All plugin specs in `lua/plugins/` are NvChad-idiomatic

### ADR-024

**Framework-Agnostic Core (Path A→C Design)**

**Status:** Accepted

**Context:** Anvil may need to support multiple frameworks in the future.

**Decision:** Structure the codebase from day one with an explicit boundary between framework-agnostic code (~80%) and framework-specific code (~20%).

**Consequences:**
- Adding a second framework requires only: new `ui/<framework>/`, new `bridge/<framework>/`, new plugin specs, strategy overrides
- `core/`, `lang/`, `ai/` remain untouched

### ADR-025

**Strategy Points in Editor Layer**

**Status:** Accepted

**Context:** The editor layer calls plugin APIs directly. Different frameworks may need different integration patterns.

**Decision:** Key functions in the editor layer are exposed as overridable module-level functions (strategy pattern).

**Consequences:**
- Simple, explicit, easy to understand
- No performance overhead
- Bridge must override before `lang.setup()` runs

### ADR-026

**Imperative Keymaps via vim.keymap.set**

**Status:** Accepted

**Decision:** All Anvil keymaps use `vim.keymap.set` directly.

**Consequences:**
- Language pack keymaps applied via `vim.keymap.set` with `{ buffer = bufnr }`
- Core keymaps in `core/keys.lua` use `vim.keymap.set`
- Plugin-specific keymaps in `lua/plugins/*.lua` use lazy.nvim `keys` field

### ADR-027

**Direct lspconfig, Not Framework LSP Abstraction**

**Status:** Accepted

**Decision:** Use `lspconfig[server].setup(opts)` directly in the editor layer.

**Consequences:**
- Must build capabilities manually
- Must manage on_attach chain manually
- Full control over LSP lifecycle

### ADR-028

**Multi-Provider Preset System for AI**

**Status:** Accepted

**Context:** The original flat 4-tier provider model (ADR-009) was insufficient:
- Real-world teams use multiple providers (cloud, local, corporate)
- Different projects have different security requirements
- Users need to switch entire AI configurations quickly
- Individual interaction types need independent model selection
- Runtime switching without restart is essential

**Decision:** Replace the flat tier system with a hierarchical **provider → model → slot → preset** architecture:

```text
┌─────────────────────────────────────────────────────────┐
│  PROVIDERS (endpoints with credentials)                 │
│  ├── openrouter (https://openrouter.ai/api/v1)         │
│  ├── ollama    (http://localhost:11434/v1)              │
│  └── corporate (https://llm.corp.internal/v1)          │
├─────────────────────────────────────────────────────────┤
│  MODELS (specific models on each provider)              │
│  ├── openrouter/claude-sonnet                           │
│  ├── openrouter/claude-haiku                            │
│  ├── ollama/qwen-coder                                  │
│  └── corporate/internal-llm                             │
├─────────────────────────────────────────────────────────┤
│  SLOTS (interaction types → model assignment)           │
│  ├── chat      → openrouter/claude-sonnet               │
│  ├── inline    → openrouter/claude-haiku                │
│  ├── agent     → openrouter/claude-sonnet               │
│  ├── architect → openrouter/claude-sonnet               │
│  ├── fast      → openrouter/claude-haiku                │
│  └── local     → ollama/qwen-coder                      │
├─────────────────────────────────────────────────────────┤
│  PRESETS (named slot configurations)                    │
│  ├── default   (cloud + local)                          │
│  ├── corporate (corporate provider only)                │
│  ├── local-only (Ollama only, no cloud)                 │
│  └── custom-1  (user-saved)                             │
└─────────────────────────────────────────────────────────┘
```

**Slot types:**
- **chat** — general AI chat conversations
- **inline** — inline code completions (minuet-ai)
- **agent** — autonomous agents (implement, debug, multi-file)
- **architect** — planning / architect mode (uses larger context)
- **fast** — quick tasks (commit messages, error explanations)
- **local** — privacy-sensitive tasks (always local provider)

**Runtime operations:**
- `:AnvilPreset [name]` — switch entire configuration
- `:AnvilSlot <slot> [model]` — change one slot
- `:AnvilSavePreset` — save current config as new preset
- Session overrides (temporary, not persisted) vs preset changes (persisted)

**Alternatives:**
- Keep flat 4-tier model — doesn't scale to multi-provider scenarios
- Per-plugin configuration — scattered, hard to switch atomically
- External config management (direnv, etc.) — too heavy, requires restart

**Consequences:**
- All AI configuration in one JSON file (`config/ai-providers.json`)
- No .env files needed for AI configuration (see ADR-029)
- CodeCompanion adapters built dynamically from slots
- External tools (Aider, OpenCode) receive credentials from the slot system
- Event bus notifies on preset/slot changes for UI updates
- Users can edit JSON directly or use in-editor UI

### ADR-029

**JSON Config Files, Not .env Variables**

**Status:** Accepted

**Context:** The original design used .env files for AI configuration (API keys, endpoints, models). This had several problems:
- Flat key-value format can't express nested structures (providers, models, presets)
- No way to switch configurations at runtime without editing files
- .env parsing is fragile (quoting, escaping, comments)
- Multiple .env files with priority rules add complexity
- Security: .env files are often accidentally committed

**Decision:** Replace .env-based configuration with JSON config files:
- `config/ai-providers.json` — AI provider/model/preset configuration
- All configuration editable in-editor via `:AnvilProviderEdit`
- `core/env.lua` simplified to only provide OS environment variable access (for PATH checks, etc.)
- No .env file loading, no .env.example, no .env priority chain

**Alternatives:**
- TOML/YAML config files — Neovim has built-in JSON support (`vim.json`), not TOML/YAML
- Lua config files — would need `dofile()` which has security implications for API keys
- Keep .env for secrets only — splits config across two systems

**Consequences:**
- Single source of truth for AI configuration
- JSON is natively supported by `vim.json.encode/decode`
- Config file can be version-controlled (with API keys gitignored or left empty)
- `core/env.lua` becomes a thin wrapper around `os.getenv()`
- Boot sequence simplified (no `env.load()` phase)
- `.env.example` removed from the project
