# Anvil — Architecture

Anvil is a comprehensive NvChad user configuration where AI is a first-class subsystem alongside LSP, languages, debugging, UI, and workflow.

## Philosophy

```text
┌─────────────────────────────────────────────────────┐
│                      ANVIL                          │
│         "One config to rule them all"               │
│                                                     │
│  1. Language-first — language defines everything    │
│  2. Consistency    — same patterns everywhere       │
│  3. AI-native      — AI is woven into every layer   │
│  4. Portable       — works on Linux and macOS       │
│  5. Declarative    — describe WHAT, not HOW         │
│  6. Discoverable   — find everything via :Anvil     │
│  7. Separable      — core logic ≠ framework chrome  │
└─────────────────────────────────────────────────────┘
```

## Layer dependency rules

```text
Bridge  → may call anything below
UI      → core/icons, core/events
Editor  → core/keys, core/icons, lang (for data)
Git     → core/events (optional)
Workflow → core/events (optional)
Lang    → core/logger, core/events
AI      → core/env, core/cache, core/logger, core/events, lang (for ai_context)
Core    → NOTHING (only vim.* built-in APIs)
```

No circular dependencies. No upward calls (core never calls ai, lang never calls editor). AI layer initializes lazily on first AI command.

## Language Pack Contract

Every language pack implements the `AnvilLangPack` interface — a single Lua table returned from `lua/anvil/lang/<name>.lua`:

```lua
---@class AnvilLangPack
---@field name        string          unique language identifier
---@field filetypes   string[]        vim filetypes this pack handles
---@field lsp         AnvilLangLSP    LSP server configuration
---@field treesitter  string[]        treesitter parsers to install
---@field formatter   AnvilLangFormatter  formatting configuration
---@field linter?     AnvilLangLinter     linting configuration (nil if via LSP)
---@field dap?        AnvilLangDAP        debug adapter configuration
---@field test?       AnvilLangTest       test framework configuration
---@field tasks?      AnvilLangTask[]     project tasks (build, run, etc.)
---@field ai?         AnvilLangAI         AI context for this language
---@field keys?       AnvilLangKeys[]     language-specific keybindings
---@field plugins?    LazyPluginSpec[]    additional plugins
```

See `lua/anvil/lang/_template.lua` for the full type definitions and `lua/anvil/lang/rust.lua` for a complete example.

## Language Engine

`lua/anvil/lang/init.lua` — the registry and aggregation engine:

- `setup(enabled_langs?)` — scans `lang/` directory, registers all packs
- `get(name)` → `AnvilLangPack?`
- `current()` → pack for current buffer's filetype
- `enabled()` → list of enabled language names
- `treesitter_ensure_installed()` → aggregated parser list
- `lsp_servers()` → aggregated server configs
- `mason_ensure_installed()` → aggregated mason tool list
- `formatters_by_ft()` → aggregated conform config
- `linters_by_ft()` → aggregated nvim-lint config
- `dap_configurations()` → aggregated DAP configs
- `neotest_adapters()` → aggregated neotest adapter specs
- `tasks()` → aggregated overseer tasks
- `extra_plugins()` → aggregated additional plugin specs
- `ai_context()` → AI context for current language
- `apply_keys(bufnr)` → apply language-specific keymaps to buffer

## Editor Layer — Strategy Points

The editor layer uses standard Neovim plugin APIs (lspconfig, nvim-cmp, nvim-dap, neotest, conform, nvim-lint). For future multi-framework support (Path C), certain functions serve as **strategy points** that a framework bridge can override:

```lua
-- editor/lsp.lua
M.register_server = function(server, opts)
  -- Default: direct lspconfig call
  require("lspconfig")[server].setup(opts)
end

-- A future AstroNvim bridge would override:
-- M.register_server = function(server, opts)
--   astrolsp.config[server] = opts
-- end
```

Strategy points exist in:
- `editor/lsp.lua` — `register_server()`, `build_capabilities()`
- `editor/dap.lua` — `register_adapter()`, `register_configuration()`
- `editor/test.lua` — `register_adapter()`

## Boot Process

```text
init.lua (NvChad bootstrap)
│
├── lazy.nvim setup
│   └── plugins/ loaded (including anvil-bridge.lua)
│
└── require("anvil").boot(opts)
    │
    ├── Phase 1: Core (synchronous)
    │   env.load() → config.apply() → logger.setup()
    │   → events.setup() → options.apply()
    │   → autocmds.setup() → keys.setup()
    │
    ├── Phase 2: Platform detection
    │   platform.apply()
    │
    ├── Phase 3: Language registration
    │   lang.setup(config.languages)
    │
    ├── Phase 4: Commands
    │   :Anvil, :AnvilChat, :AnvilAsk, :AnvilIndex, etc.
    │
    └── Phase 5: Ready
        events.emit("ready")
```

AI layer initializes lazily on first AI command.

## Future: Path A → C (multi-framework)

When adding a second framework (e.g., AstroNvim):

1. Create `lua/anvil/ui/astronvim/` — theme, statusline
2. Create `lua/anvil/bridge/astronvim/` — boot integration, strategy overrides
3. Create a separate `lua/plugins-astronvim/` (or separate repo)
4. Override strategy points in editor layer
5. `core/`, `lang/`, `ai/` — **zero changes**
