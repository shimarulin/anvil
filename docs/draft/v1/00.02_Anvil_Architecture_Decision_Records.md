# Anvil — Architecture Decision Records

Architectural decisions made during Anvil design, with context,
alternatives considered, and rationale. This document serves as
a living reference for contributors and AI agents working on the
codebase.

## Format

Each decision follows a lightweight ADR format:

- **ID**: Sequential identifier
- **Status**: Accepted / Superseded / Deprecated
- **Context**: Why the decision was needed
- **Decision**: What was decided
- **Alternatives**: What else was considered
- **Consequences**: What follows from this decision

### ADR-001

**NVIM_APPNAME Isolation**

**Status:** Accepted

**Context:**
Users may have an existing Neovim configuration they don't want to
disrupt. Anvil needs to coexist with other configs on the same machine.

**Decision:**
Use Neovim's built-in `NVIM_APPNAME` mechanism (available since 0.9)
to run Anvil in a completely isolated environment. All paths — config,
data, state, cache — are scoped to the app name.

```bash
NVIM_APPNAME=astronvim nvim   # uses ~/.config/astronvim/
nvim                           # uses ~/.config/nvim/ (untouched)
```

**Alternatives:**
- Separate Neovim binary — impractical, version management nightmare
- Docker container — too heavy for an editor
- Manual XDG path overrides — fragile, not all plugins respect them

**Consequences:**
- Clean separation between configurations
- Mason packages, plugin data, sessions are all isolated
- Alias `astro` provides convenient access
- Scripts must always set `NVIM_APPNAME` for headless operations

### ADR-002

**Language-First Architecture**

**Status:** Accepted

**Context:**
Traditional Neovim configs scatter language support across multiple
files: LSP config here, formatter there, DAP somewhere else, test
runner in yet another place. Adding a new language requires touching
5-10 files. Removing one is even harder.

**Decision:**
Each language is a self-contained pack — a single Lua table that
declares everything: LSP, treesitter, formatter, linter, DAP, test
runner, tasks, AI context, keymaps, and extra plugins. The lang
engine reads these packs and distributes their declarations to the
appropriate plugin configurations.

```
Add language    = create 1 file
Remove language = delete 1 file
```

**Alternatives:**
- AstroCommunity packs — good but not customizable enough, can't
  add AI context or custom tasks
- Per-plugin configuration — the traditional approach, doesn't scale
- Language-specific plugin collections (e.g., go.nvim does everything) —
  creates vendor lock-in to one plugin's decisions

**Consequences:**
- Consistency: every language has the same structure
- Discoverability: look at one file to understand everything about a language
- The lang engine (`anvil/lang/init.lua`) becomes a critical component
- Lang packs must follow the `AnvilLangPack` contract strictly
- Some languages need escape hatches (see ADR-004)

### ADR-003

**Single-File Language Packs**

**Status:** Accepted

**Context:**
The language pack could be a directory with multiple files (lsp.lua,
dap.lua, test.lua, etc.) or a single file returning a table.

**Decision:**
Single file per language. The `AnvilLangPack` type contract is
comprehensive but flat — one table with all declarations.

**Alternatives:**
- Directory per language (`lang/rust/init.lua`, `lang/rust/dap.lua`, etc.) —
  more files to navigate, harder to see the full picture
- Separate registration files — loses the "one place" benefit

**Consequences:**
- Files can get long (150-300 lines for complex languages like Rust)
- But everything is in one place — grep for "rust" and you find it all
- The contract type (`AnvilLangPack`) serves as documentation
- Easy to copy `_template.lua` and fill in for a new language

### ADR-004

**Lang Engine Flags: `managed_by_plugin`, `managed_by_lsp`**

**Status:** Accepted

**Context:**
Most languages follow the standard path: LSP via lspconfig, formatter
via conform, linter via nvim-lint. But some languages have specialized
plugins that manage these components themselves:

- **Rust**: rustaceanvim manages rust-analyzer directly (not lspconfig)
- **Rust**: rustfmt runs through rust-analyzer, not conform

The lang engine needs to know when to skip its standard registration.

**Decision:**
Two boolean flags in the lang pack:

```lua
lsp = {
  server = "rust_analyzer",
  managed_by_plugin = true,  -- skip lspconfig registration
  ...
},
formatter = {
  tool = "rustfmt",
  managed_by_lsp = true,     -- skip conform registration
  ...
},
```

The lang engine checks these flags:
- `managed_by_plugin = true` → don't add to lspconfig servers
- `managed_by_lsp = true` → don't add to conform formatters_by_ft

Mason still installs the tools regardless of these flags.

**Alternatives:**
- Separate the Rust config entirely from the lang system — loses
  consistency, Rust becomes a special case everywhere
- Have rustaceanvim read from the lang pack — too tightly coupled
- Use a different lang pack format for "plugin-managed" languages —
  unnecessary complexity

**Consequences:**
- The lang engine remains the single source of truth
- Specialized plugins get full control where needed
- Mason install list is always complete
- Two new fields to document in the `AnvilLangPack` type

### ADR-005

**Dual LSP Support (`extra_servers`)**

**Status:** Accepted

**Context:**
Python benefits from running two LSP servers simultaneously:
basedpyright for type checking and ruff for lint code actions.
They complement each other — basedpyright excels at types, ruff
excels at quick fixes. This pattern may apply to other languages
in the future.

**Decision:**
Add `extra_servers` field to the LSP section of lang packs:

```lua
lsp = {
  server = "basedpyright",       -- primary
  extra_servers = {
    {
      server = "ruff",           -- secondary
      on_attach = function(client, bufnr)
        client.server_capabilities.hoverProvider = false
      end,
    },
  },
},
```

The lang engine registers all servers (primary + extras) in lspconfig
and includes all in Mason's ensure_installed list.

**Alternatives:**
- Run only one LSP — lose either type checking quality or lint actions
- Use nvim-lint for ruff instead of LSP — lose code actions
- Hardcode the dual-LSP pattern outside the lang pack — loses
  consistency

**Consequences:**
- Capability conflicts must be resolved in `on_attach` (e.g., disable
  hover on ruff since basedpyright provides better hover)
- Formatting must be disabled on both servers when conform handles it
- The lang engine's `lsp_servers()` and `mason_ensure_installed()`
  must iterate over `extra_servers`
- Pattern is reusable for other languages (e.g., C++ with clangd + clang-tidy)

### ADR-006

**Formatter Chains**

**Status:** Accepted

**Context:**
Go requires two formatters in sequence: `goimports` (manages imports)
then `gofumpt` (strict formatting). Python similarly benefits from
`ruff_organize_imports` then `ruff_format`. Conform.nvim supports
running multiple formatters in order.

**Decision:**
Add `formatter.chain` field to lang packs:

```lua
formatter = {
  tool = "goimports",                       -- primary (for mason install)
  chain = { "goimports", "gofumpt" },       -- run in order
  format_on_save = true,
},
```

The lang engine's `formatters_by_ft()` uses `chain` if present,
otherwise falls back to `{ tool }`.

**Alternatives:**
- Use only one formatter — lose import management or strict formatting
- Configure conform directly outside the lang pack — loses consistency
- Use LSP formatting for everything — not all LSPs format well

**Consequences:**
- `formatter.tool` is always the primary tool (used for mason install)
- `formatter.chain` overrides the conform configuration
- Custom conform formatters (like `ruff_organize_imports`) must be
  defined in the editor layer's conform config
- The order in the chain matters — imports first, then formatting

### ADR-007

**conform.nvim + nvim-lint, Not null-ls**

**Status:** Accepted

**Context:**
null-ls (now none-ls) was the traditional way to integrate external
formatters and linters into Neovim's LSP framework. It was archived
by the original author and forked as none-ls, but the architecture
has fundamental issues: it pretends external tools are LSP servers,
which creates complexity and confusion.

**Decision:**
Use purpose-built tools:
- **conform.nvim** for formatting (by stevearc)
- **nvim-lint** for linting (by mfussenegger)

Both are actively maintained, focused on their specific task, and
have simpler APIs.

**Alternatives:**
- none-ls (null-ls fork) — works but architecturally questionable,
  community momentum is shifting away
- LSP-only formatting — not all languages have good LSP formatters
- Manual autocmd-based formatting — too much boilerplate

**Consequences:**
- Two plugins instead of one, but each is simpler
- Lang packs declare `formatter` and `linter` separately
- Format-on-save is handled by conform, not LSP
- Some LSP servers need their formatting disabled (`on_attach`)
- Both integrate cleanly with the lang pack system

### ADR-008

**CodeCompanion as Primary AI, Not Avante**

**Status:** Accepted

**Context:**
Multiple Neovim AI chat plugins exist: Avante, CodeCompanion,
ChatGPT.nvim, etc. The AI ecosystem needs a primary chat/agent
interface that supports:
- OpenAI-compatible API (any provider)
- Tool use / function calling
- MCP integration
- Slash commands and variables
- Customizable prompts
- Inline code actions

**Decision:**
CodeCompanion as the primary AI interface.

**Alternatives:**
- **Avante** — good UI (VSCode Copilot-like sidebar), but:
  - Less flexible prompt system
  - Weaker tool/agent support
  - Tighter coupling to specific providers
  - Less extensible slash commands
- **ChatGPT.nvim** — simpler, but lacks agent capabilities
- **Custom solution** — too much maintenance burden

**Rationale for CodeCompanion:**
- Fully open source, active development
- OpenAI-compatible adapter works with any provider
- Rich slash command system (`/project`, `/diagnostics`, `/url`, etc.)
- Variable system (`@buffer`, `@lsp`, `@viewport`)
- MCP integration via mcphub.nvim extension
- Customizable prompt library (architect mode, agents, etc.)
- Inline code actions with diff view
- Fidget.nvim integration for progress indication

**Consequences:**
- All AI chat workflows go through CodeCompanion
- Custom slash commands provide context from Anvil's subsystems
- Prompt library serves as the "agent" layer
- Avante could be added as an optional alternative later
- AI keymaps are unified under `<leader>a`

### ADR-009

**Unified AI Provider Configuration**

**Status:** Accepted

**Context:**
Multiple AI tools (CodeCompanion, minuet-ai, wtf.nvim, external
tools like aider/goose) all need API endpoints and keys. Without
centralization, the same credentials are scattered across configs.

**Decision:**
Single provider configuration module (`anvil/ai/providers.lua`)
that reads from environment variables and `.env` files. All AI
tools reference this module.

```
.env → anvil/ai/providers.lua → CodeCompanion
                               → minuet-ai
                               → wtf.nvim
                               → aider (env vars)
                               → goose (env vars)
```

Four provider tiers:
- **main** — primary model for agents and chat
- **fast** — smaller model for completions and small tasks
- **planner** — large context model for architect mode
- **local** — Ollama/local model as fallback

**Alternatives:**
- Per-plugin configuration — duplicated credentials, easy to desync
- Neovim global variables — not secure, visible in `:let`
- Hardcoded in Lua files — can't change without editing config

**Consequences:**
- One place to change API keys or switch providers
- `.env` file is gitignored (security)
- External tools receive credentials via environment variables
- `:AIConfig` command shows current configuration
- Health check verifies API key presence

### ADR-010

**External AI Tools via toggleterm**

**Status:** Accepted

**Context:**
Heavy AI tasks (large refactors, multi-file changes, autonomous
coding) benefit from specialized external tools: aider, goose,
opencode, plandex. These are CLI applications that need a terminal.

**Decision:**
Launch external AI tools as toggleterm terminals within Neovim.
Each tool gets a dedicated Terminal instance with pre-configured
environment variables from the unified provider config.

Context transfer: `AIExternalContext <tool>` command builds context
from Anvil's context-builder (project index, diagnostics, treesitter,
tests) and passes it to the external tool.

**Alternatives:**
- Run in external terminal — lose integration, can't pass context
- Build all capabilities into CodeCompanion — unrealistic, each tool
  has unique strengths
- Use Neovim's built-in terminal — less feature-rich than toggleterm

**Consequences:**
- External tools run inside Neovim's UI
- Context can be passed from editor to external tool
- File changes made by external tools are picked up by Neovim
  (autoread)
- Each tool has `:Aider`, `:Goose`, `:OpenCode`, `:Plandex` commands
- Keymaps under `<leader>A` for external tools

### ADR-011

**MCP as Extensibility Standard**

**Status:** Accepted

**Context:**
AI agents need access to external resources: databases, APIs, file
systems, web search, documentation. Each integration could be built
as a custom Neovim plugin, but this doesn't scale.

**Decision:**
Use Model Context Protocol (MCP) as the standard for connecting
AI agents to external tools. MCP servers are managed by mcphub.nvim
and available to CodeCompanion via its MCP extension.

Standard MCP servers:
- filesystem — read/write files, list directories
- fetch — HTTP requests, read documentation
- memory — persistent knowledge graph across sessions
- git — git operations
- sequential-thinking — step-by-step reasoning
- brave-search — web search (optional, needs API key)
- postgres — database queries (optional, needs connection string)

**Alternatives:**
- Custom tool implementations in CodeCompanion — doesn't scale,
  not reusable
- Neovim-specific integrations — limited to Neovim ecosystem
- No external tool access — severely limits agent capabilities

**Consequences:**
- AI agents can access databases, APIs, documentation
- New capabilities = install new MCP server (no Neovim code changes)
- MCP servers run as separate processes (managed by mcp-hub)
- Configuration in `~/.config/mcphub/servers.json`
- Some servers need API keys or connection strings

### ADR-012

**rustaceanvim, Not rust-tools.nvim**

**Status:** Accepted

**Context:**
rust-tools.nvim was the standard Rust plugin for Neovim but has
been archived/deprecated. rustaceanvim (by mrcjkb) is its spiritual
successor with a different architecture.

**Decision:**
Use rustaceanvim v5 for Rust support.

**Key difference:** rustaceanvim manages rust-analyzer's lifecycle
directly — it does NOT use lspconfig. This is why the Rust lang pack
uses `managed_by_plugin = true`.

**Alternatives:**
- rust-tools.nvim — deprecated, no longer maintained
- Plain lspconfig + rust-analyzer — works but loses: expanded macro
  view, runnables/debuggables picker, crate graph, join lines,
  enhanced hover actions, and other Rust-specific features
- Manual rust-analyzer setup — too much boilerplate

**Consequences:**
- Configuration via `vim.g.rustaceanvim` (read at startup)
- LSP settings live in the lang pack but are applied by rustaceanvim
- DAP integration is built into rustaceanvim (codelldb)
- Runnables/debuggables/testables provide Rust-specific workflows
- The lang engine must not register rust_analyzer in lspconfig

### ADR-013

**basedpyright + ruff Dual LSP for Python**

**Status:** Accepted

**Context:**
Python's tooling landscape has fragmented: pyright for types, ruff
for linting, black for formatting, isort for imports. Each tool
has different strengths.

**Decision:**
Run two LSP servers simultaneously:
- **basedpyright** — type checking, completion, hover, goto definition
- **ruff** (LSP mode) — code actions for auto-fixing lint issues

Capability conflicts are resolved in `on_attach`:
- ruff's hover is disabled (basedpyright is better)
- Both servers' formatting is disabled (conform handles it)

**Alternatives:**
- pyright only — no lint code actions
- pylsp — slower, less accurate type checking
- ruff only — no type checking
- jedi-lsp — weaker type support

**Why basedpyright over pyright:**
- Fork with additional features (inlay hints improvements, etc.)
- Fully compatible with pyright
- More actively developed
- Better Neovim integration

**Consequences:**
- Two LSP servers running for Python files
- `extra_servers` mechanism in lang engine (ADR-005)
- Slightly higher memory usage (acceptable)
- Code actions from both servers appear in the same menu
- Must carefully manage capabilities to avoid conflicts

### ADR-014

**typescript-tools.nvim for TypeScript**

**Status:** Accepted

**Context:**
TypeScript LSP options in Neovim:
- ts_ls (built-in, basic)
- vtsls (fast, community)
- typescript-tools.nvim (wraps tsserver, extra features)

**Decision:**
Use typescript-tools.nvim as the primary TypeScript LSP.

**Rationale:**
- Provides commands not available in other servers:
  - `TSToolsOrganizeImports`
  - `TSToolsRemoveUnusedImports`
  - `TSToolsAddMissingImports`
  - `TSToolsRenameFile` (renames file + updates all imports)
  - `TSToolsGoToSourceDefinition` (skips .d.ts, goes to .ts)
  - `TSToolsFixAll`
- Better diagnostic filtering (can suppress noisy TS errors)
- Separate diagnostic server for performance

**Alternatives:**
- **vtsls** — faster startup, but fewer features. Good alternative
  if typescript-tools causes issues. Can be swapped by changing
  the lang pack's `lsp.server`.
- **ts_ls** — too basic for professional TypeScript development

**Critical rule:** Never run typescript-tools AND vtsls simultaneously.
The lang pack must use one or the other.

**Consequences:**
- TypeScript-specific keymaps (`<leader>lo`, `<leader>lu`, etc.)
- Formatting disabled on the TS server (prettierd via conform)
- Must install `typescript-language-server` via Mason (used by
  typescript-tools internally)

### ADR-015

**ruff Replaces black + flake8 + isort**

**Status:** Accepted

**Context:**
Traditional Python tooling uses three separate tools:
- black (formatting)
- flake8 (linting)
- isort (import sorting)

Each needs separate configuration, installation, and CI setup.

**Decision:**
Use ruff for all three: `ruff format` (replaces black),
`ruff check` (replaces flake8 + pylint + isort + 800 more rules).

**Rationale:**
- 10-100x faster than black/flake8 (written in Rust)
- Output-compatible with black
- Supports 800+ lint rules from multiple tools
- Single configuration in `pyproject.toml`
- Has LSP mode for code actions
- Active development by Astral (also makes uv)

**Alternatives:**
- black + flake8 + isort — slower, three configs, three tools
- autopep8 — less opinionated, less popular
- yapf — Google's formatter, less community adoption

**Consequences:**
- Formatter chain: `ruff_organize_imports` → `ruff_format`
- Custom conform formatter definition for `ruff_organize_imports`
- Linter: `ruff` via nvim-lint
- LSP: `ruff` as extra_server for code actions
- All configuration in `pyproject.toml` under `[tool.ruff]`

### ADR-016

**lazydev.nvim, Not neodev.nvim**

**Status:** Accepted

**Context:**
Neovim Lua development requires type information for the vim.* API,
vim.uv (libuv), and installed plugin types. neodev.nvim was the
standard solution but has been superseded.

**Decision:**
Use lazydev.nvim (by folke, same author as neodev).

**Rationale:**
- neodev.nvim is in maintenance mode, author recommends lazydev
- lazydev is faster (lazy-loads type libraries on demand)
- Better integration with lua_ls workspace management
- Supports library loading based on word patterns
  (e.g., load luvit types only when `vim.uv` is found)
- Integrates with nvim-cmp for type-aware completion

**Alternatives:**
- neodev.nvim — deprecated by its own author
- Manual .luarc.json — works but doesn't adapt to context
- No type support — poor development experience

**Consequences:**
- `vim.*` completion works out of the box
- `vim.uv` types loaded on demand via luvit-meta
- lazy.nvim plugin spec types available
- lua_ls `checkThirdParty` must be `false` (lazydev handles it)
- lua_ls `format.enable` must be `false` (stylua handles it)

### ADR-017

**neotest-golang, Not neotest-go**

**Status:** Accepted

**Context:**
Two neotest adapters exist for Go:
- neotest-go (nvim-neotest) — original, basic
- neotest-golang (fredrikaverpil) — newer, more features

**Decision:**
Use neotest-golang (fredrikaverpil/neotest-golang).

**Rationale:**
- More actively maintained
- Better test discovery
- Supports testify framework
- DAP integration (debug individual tests via delve)
- Better handling of table-driven tests
- Configurable test arguments (race detection, timeout)

**Alternatives:**
- neotest-go — works but less maintained, fewer features
- go.nvim test runner — different UI, doesn't integrate with neotest
- Overseer tasks only — no inline test results

**Consequences:**
- Test results appear inline in the editor
- Individual tests can be debugged via delve
- `go_test_args` configurable in the lang pack
- Depends on `nvim-neotest/nvim-nio`

### ADR-018

**selene, Not luacheck**

**Status:** Accepted

**Context:**
Two Lua linters exist:
- luacheck — established, widely used
- selene — newer, written in Rust, more modern

**Decision:**
Use selene as the primary Lua linter.

**Rationale:**
- Faster (written in Rust)
- Better default rules
- Understands Neovim's vim global without extra config
- Standard library definitions (vim.yml)
- More modern diagnostics

**Alternatives:**
- luacheck — works well, more documentation, but slower and
  requires more configuration for Neovim Lua
- lua_ls diagnostics only — misses some patterns that dedicated
  linters catch

**Consequences:**
- `selene.toml` in project root for configuration
- `vim.yml` standard library for Neovim globals
- Both selene and luacheck available as overseer tasks
- Mason installs selene

### ADR-019

**Telescope as Universal Picker**

**Status:** Accepted

**Context:**
Multiple picker/fuzzy-finder plugins exist: Telescope, fzf-lua,
mini.pick, snacks.picker. The picker is used extensively throughout
Anvil: file finding, grep, LSP navigation, git, AI chat history,
harpoon, undo, etc.

**Decision:**
Telescope as the single picker for everything.

**Rationale:**
- Most mature ecosystem (extensions for everything)
- Native fzf sorter for performance
- Consistent UI across all use cases
- Extensions: file-browser, undo, live-grep-args, ui-select
- Used by many plugins as their default picker

**Alternatives:**
- **fzf-lua** — faster for large projects, but fewer extensions
- **mini.pick** — minimal, but limited extension ecosystem
- **snacks.picker** — new, promising, but not yet mature

**Consequences:**
- All picker interactions go through Telescope
- Extensions loaded: fzf, ui-select, file-browser, undo, live-grep-args
- `telescope-ui-select` replaces vim.ui.select globally
- Performance tuned with fzf-native sorter
- File ignore patterns centralized in Telescope config

### ADR-020

**Overseer for Task Management**

**Status:** Accepted

**Context:**
Running project tasks (build, test, lint, etc.) needs a structured
approach. Options: toggleterm commands, custom Lua functions, or
a task runner plugin.

**Decision:**
Use overseer.nvim as the task management layer.

**Rationale:**
- Structured task definitions with templates
- Auto-detection from Makefile, package.json, Cargo.toml, etc.
- Task output captured and searchable
- Integration with AI (send task output to CodeCompanion)
- Persistent task list with status tracking
- Can use toggleterm as execution strategy

**Alternatives:**
- toggleterm commands — no structure, no status tracking
- Custom Lua functions — too much maintenance
- vim-dispatch — less feature-rich, Vimscript-oriented
- neotest for everything — neotest is for tests, not general tasks

**Consequences:**
- Lang packs declare `tasks` array
- Tasks are registered with overseer on filetype detection
- `<leader>or` opens task picker for current filetype
- Task output can be sent to AI for analysis
- Overseer UI shows running/completed/failed tasks

### ADR-021

**Layered Architecture with Event Bus**

**Status:** Accepted

**Context:**
Anvil has multiple subsystems (core, lang, AI, editor, UI, git,
workflow) that need to communicate without tight coupling.

**Decision:**
Five-layer architecture with an event bus:

```
Core → Lang → Editor → AI → UI
         ↕ event bus ↕
```

Layers:
1. **Core** — env, events, cache, logger, keys, options (loads first)
2. **Lang** — language packs, registry (loads second)
3. **Editor** — treesitter, LSP, cmp, format, lint, DAP, test
4. **AI** — providers, context, agents, completion, MCP, tools
5. **UI** — theme, statusline, bufferline, explorer, picker, dashboard

The event bus (`anvil.core.events`) allows cross-layer communication:
- `anvil:ready` — all layers loaded
- `anvil:lang:attached` — language pack activated for buffer
- `anvil:ai:response` — AI response received

**Alternatives:**
- Flat plugin list — no structure, hard to reason about dependencies
- Strict module imports — creates tight coupling
- Single monolithic config — unmaintainable at scale

**Consequences:**
- Each layer can be developed and tested independently
- Events decouple producers from consumers
- Boot sequence is deterministic (core → lang → editor → AI → UI)
- Lazy loading is natural (AI layer loads on first AI command)
- Health check can verify each layer independently

### ADR-022

**minuet-ai for Inline Completion, Off by Default**

**Status:** Accepted

**Context:**
Inline AI completion (ghost text suggestions while typing) is useful
but can be distracting and expensive (API calls on every keystroke).
The user should control when it's active.

**Decision:**
Use minuet-ai.nvim for inline completion, **disabled by default**.
Toggle with `<F2>` or `:MinuetToggle`.

**Rationale:**
- Uses the same OpenAI-compatible API as CodeCompanion
- Configurable debounce (600ms default)
- Multiple suggestions with Alt+]/Alt+[
- Accept with Alt+a, accept line with Alt+l
- No subscription required (unlike Copilot/Supermaven)

**Alternatives:**
- **Supermaven** — fast, free tier, but proprietary
- **Copilot** — requires subscription
- **codeium** — free but proprietary
- **Always-on completion** — expensive, distracting

**Consequences:**
- No AI completion noise by default
- User explicitly enables when needed
- Uses the "fast" provider tier (smaller, cheaper model)
- `auto_trigger_ft = {}` means no filetypes auto-trigger
- Status shown in statusline when active

### ADR-023

**Symlink Strategy for User Config**

**Status:** Accepted

**Context:**
The user's Anvil configuration needs to be in a git repository for
version control, but AstroNvim expects it at a specific path within
its config directory.

**Decision:**
Store the user config in a separate git repository (e.g.,
`~/repos/my-astronvim-config/`) and symlink it into AstroNvim's
expected location (`~/.config/astronvim/lua/user/`).

```bash
ln -s ~/repos/my-astronvim-config ~/.config/astronvim/lua/user
```

**Alternatives:**
- Put config directly in AstroNvim's directory — mixes upstream
  and user code in one git repo
- Git submodule — complex, merge conflicts
- Copy files on change — manual, error-prone

**Consequences:**
- User config has its own git history
- AstroNvim can be updated with `git pull` without conflicts
- The symlink survives AstroNvim updates
- `.ref/` files provide AstroNvim context for AI agents
- `sync-ref.sh` keeps reference files up to date
