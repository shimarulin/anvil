# Rule: File Output Format

Every **project file** (code, config, or documentation to be written to disk)
must use this structure in your Markdown output:

```text
### `path/to/file.ext`

Optional description.

<!-- file: path/to/file.ext -->
​```lang
content
​```
```

## Requirements

1. **Marker** `<!-- file: path/to/file.ext -->`
   - Exactly one space after `<!-- file:` and one space before `-->`.
   - On its own line, **immediately before** the opening fence — no blank line.
   - Path is **project-relative** (`src/main.py`, not `/home/user/src/main.py`).
   - Only HTML comment syntax. No alternatives (`// file:`, `# file:`, etc.).

2. **Heading** `### \`path/to/file.ext\``
   - Level-3 heading with the path in inline code backticks, nothing else.
   - Must match the marker path **exactly**.
   - If they diverge, update the heading to match the marker.
   - Descriptions go on a separate line between heading and marker.

3. **Language tag** on the fence is required (`python`, `bash`, `yaml`, `text`, …).

4. **Fence depth**: outer fence must be **strictly longer** than any fence
   inside the content.

   TL;DR: Fence rule: outer fence = max(inner fences) + 1 backtick; minimum 3. If no inner fences, use 3.

   | Inner fences | Outer fence |
   |---|---|
   | None | ` ``` ` (3) |
   | ` ``` ` (3) | ` ```` ` (4) |
   | ` ```` ` (4) | ` ````` ` (5) |
   | *N* backticks | *N + 1* or more |

5. **Project file vs illustrative snippet** — decision criterion:
   - Can you name a concrete project-relative path? → **project file** → heading + marker.
   - No real path (CLI demo, conceptual example)? → **illustrative snippet** → no heading, no marker, precede with explanatory text.
   - Uncertain? → ask the user.
   - Partial file updates (diffs, fragments) → snippet with heading and line numbers, no marker.

6. **Nested Markdown**: when a Markdown project file embeds other project
   files, inner code blocks **must** carry their own heading + marker (they
   will be written to disk and extracted recursively).

7. **Absolute paths forbidden** in markers. Store files under a
   project-relative path (e.g. `deploy/nginx/nginx.conf`) and note the
   target location in the description.

## Key examples

### Ordinary project file

### `src/main.py`

<!-- file: src/main.py -->
```python
print("hello")
```

### Markdown file containing fenced code

### `docs/README.md`

<!-- file: docs/README.md -->
````markdown
# README

```bash
echo "hello"
```
````

### Markdown project file embedding other project files

### `docs/architecture.md`

<!-- file: docs/architecture.md -->
`````markdown
# Architecture

### `src/app.py`

<!-- file: src/app.py -->
```python
def main():
    pass
```

### `src/utils.py`

<!-- file: src/utils.py -->
```python
def helper():
    pass
```
`````

### ❌ Wrong — blank line between marker and fence

```text
<!-- file: src/main.py -->

​```python
print("hello")
​```
```

Correct — marker immediately before fence:

```text
<!-- file: src/main.py -->
​```python
print("hello")
​```
```

### ❌ Wrong — description in heading

```text
### `src/main.py` — entry point
```

Correct — description on a separate line:

```text
### `src/main.py`

Entry point.
```

## Compliance checklist

Before outputting every code block, verify:

1. Does this block represent a file to be written to disk?
2. Can I name its project-relative path?
3. Is there a `### \`path\`` heading above it?
4. Is there `<!-- file: path -->` **immediately** before the fence?
5. Do the heading and marker paths match exactly?
6. Is the outer fence longer than any inner fence?

If (1) or (2) is *no* → omit heading and marker (illustrative snippet).
If (3)–(6) is *no* → fix before outputting.
