# Rule: File Output Format

When outputting project files, follow ALL of these rules:

## 1. Structure per file

### `path/to/file.ext`

Optional description or notes.

<!-- file: path/to/file.ext -->
```lang
content
```

- The Markdown heading (`### \`path\``) makes output human-readable.
- The HTML marker (`<!-- file: path -->`) on the line **immediately before**
  the opening fence enables automated extraction. Never omit it for project
  files.
- Code blocks **without** the `<!-- file: -->` marker are treated as
  illustrative snippets and will be ignored by the extractor.

### Heading vs marker: priority and consistency

The path appears twice — in the heading (for humans) and in the marker (for
the extractor). They **must** match.

- The **marker is authoritative**: the extractor uses `<!-- file: path -->`
  to determine the output path.
- The heading is cosmetic but **must agree** with the marker so a human
  reader is never misled.
- If you encounter an existing file where the heading and marker diverge,
  **update the heading** to match the marker.

## 2. When to apply this rule

This rule applies whenever you output content of a file **for which the path
is known** — regardless of where that content appears:

| Situation | Apply rule? |
|---|---|
| Outputting a project file in your response | **Yes** |
| Embedding a project file inside a Markdown file that is itself part of your output | **Yes** (recursive) |
| Showing an illustrative snippet (no real file path) | No — omit the marker |

When in doubt: if you can name a file path for the code block, treat it as a
project file and use the full heading + marker structure.

## 3. Markdown file content (or any content containing triple backticks)

When the file itself contains triple backticks (e.g. `.md` files with fenced
code blocks), wrap the entire block in **quadruple** backticks so the inner
fences render correctly:

### `docs/README.md`

<!-- file: docs/README.md -->
````markdown
# Title

Some text

```bash
echo "hello"
```
````

## 4. Markers inside Markdown project files

When a Markdown project file **itself contains code blocks that represent
project files** (e.g. a design document showing file contents), those inner
code blocks **must also carry `<!-- file: -->` markers**.

The markers are part of the file's content — they will be written into the
Markdown file on disk so that the same extractor can process it recursively.

**Example — a design doc that embeds two project files:**

### `docs/architecture.md`

<!-- file: docs/architecture.md -->
`````markdown
# Architecture

## Entry point

### `src/main.py`

<!-- file: src/main.py -->
```python
print("hello")
```

### `src/utils.py`

<!-- file: src/utils.py -->
```python
def helper():
    pass
```
`````

Note: the outer fence uses **quintuple** backticks because the content
already contains quadruple backticks (or triple). Always use a fence that is
at least one backtick longer than the longest fence inside the content.

### When to omit inner markers

Omit `<!-- file: -->` inside a Markdown project file **only** when a code
block is truly illustrative (e.g. a shell session example, a snippet that
does not correspond to any real file). If the code block has a
`### \`path/to/file\`` heading above it, it **must** have the marker.

### Descriptions between heading and code block

You **may** place descriptive text — including illustrative code blocks —
between the heading and the marker. The extractor will ignore any code block
that lacks a `<!-- file: -->` marker, so there is no ambiguity:

### `src/main.py`

This replaces the old approach:

```python
# old code — illustrative only, no marker
```

<!-- file: src/main.py -->
```python
# new code — this will be extracted
```

## 5. Multiple files

Output files sequentially, each with its own heading and marker:

### `src/main.py`

Entry point.

<!-- file: src/main.py -->
```python
print("hello")
```

### `src/utils.py`

<!-- file: src/utils.py -->
```python
def helper():
    pass
```

## 6. File paths

All paths are **relative to the project root**. Never use absolute system
paths (`/etc/...`, `/usr/...`) as the marker path.

If a file is ultimately destined for an absolute location on a target system
(e.g. inside a Docker container, deployed via Ansible), store it locally
under a project-relative path that reflects its purpose (e.g.
`deploy/nginx/nginx.conf`) and document the real target path in a comment or
description. The project directory is the single source of truth.

## 7. Fence length rules

| Content contains       | Outer fence length |
|------------------------|--------------------|
| No backtick fences     | 3 (triple)         |
| Triple backtick fences | 4 (quadruple)      |
| Quadruple fences       | 5 (quintuple)      |
| *N*-length fences      | *N + 1* or more    |

Always inspect the content and pick a fence length that is **strictly
longer** than any fence inside.

## 8. Summary

| Element | Required? | Purpose |
|---|---|---|
| `### \`path\`` heading | Yes | Human readability, navigation |
| `<!-- file: path -->` marker | Yes | Automated file extraction |
| Heading ↔ marker path match | Yes | Prevent human/machine mismatch |
| Language tag on fence | Yes | Syntax highlighting |
| Description between heading and code | Optional | Context for the reader |
| Markers inside Markdown content | Yes, for project-file code blocks | Recursive extraction |
| Correct fence length | Yes | Proper rendering of nested fences |
| Relative paths only | Yes | Project dir is source of truth |
