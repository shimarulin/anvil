# Rule: File Output Format

Every **project file** (code, config, or documentation to be written to disk)
must use this structure in your Markdown output:

````markdown
### `path/to/file.ext`

Optional description.

<!-- file: path/to/file.ext -->
​```lang
content
​```
````

Every **patch to an existing file** (partial modification via unified diff)
must use this structure:

````markdown
### `path/to/file.ext`

Description of what changes and why.

<!-- patch: path/to/file.ext -->
​```diff
--- a/path/to/file.ext
+++ b/path/to/file.ext
@@ -10,6 +10,8 @@
 context line
+added line
 context line
​```
````

## Requirements

### Markers

1. **Two marker types**:
   - `<!-- file: path/to/file.ext -->` — full file (overwrite)
   - `<!-- patch: path/to/file.ext -->` — unified diff (partial update)

2. **Marker syntax**:
   - Exactly one space after `<!-- file:` or `<!-- patch:` and one space before `-->`.
   - On its own line, **immediately before** the opening fence — no blank line between marker and fence.
   - Path is **project-relative** (`src/main.py`, not `/home/user/src/main.py`).
   - Only HTML comment syntax. No alternatives (`// file:`, `# file:`, etc.).
   - **Every project file or patch block MUST have a marker. No exceptions.**

3. **Heading** `### \`path/to/file.ext\``
   - Level-3 heading with the path in inline code backticks, nothing else.
   - Must match the marker path **exactly**.
   - If they diverge, update the heading to match the marker.
   - Descriptions go on a separate line between heading and marker.

4. **Language tag** on the fence is required (`python`, `bash`, `yaml`, `diff`, `text`, …).
   Patch blocks always use the `diff` language tag.

5. **Patch format**: standard unified diff.
   - `--- a/path` and `+++ b/path` header lines.
   - `@@ -line,count +line,count @@` hunk headers.
   - Context lines (` `), additions (`+`), deletions (`-`).
   - Minimum 3 context lines around each change (standard `diff -U3`).

### Fence depth

Outer fence must be **strictly longer** than any fence inside the content.

TL;DR: outer fence = max(inner fences) + 1 backtick; minimum 3.
If no inner fences, use 3.

| Inner fences | Outer fence |
|---|---|
| None | ` ``` ` (3) |
| ` ``` ` (3) | ` ```` ` (4) |
| ` ```` ` (4) | ` ````` ` (5) |
| *N* backticks | *N + 1* or more |

### Choosing between file and patch

| Situation | Marker | Why |
|---|---|---|
| New file | `<!-- file: -->` | Nothing to patch |
| Small existing file, most lines change | `<!-- file: -->` | Patch would be longer than full file |
| Large existing file, few lines change | `<!-- patch: -->` | Saves space, shows intent clearly |
| Existing file, adding a section | `<!-- patch: -->` | Context lines anchor the insertion |
| Uncertain whether file exists | `<!-- file: -->` | Safe default — always works |

### Choosing between project file and illustrative snippet

- Can you name a concrete project-relative path? → **project file** → heading + marker.
- No real path (CLI demo, conceptual example)? → **illustrative snippet** → no heading, no marker, precede with explanatory text.
- Uncertain? → ask the user.
- Partial file updates (diffs, fragments) → `<!-- patch: -->` with heading.

### Absolute paths

Forbidden in markers. Store files under a project-relative path
(e.g. `deploy/nginx/nginx.conf`) and note the target location in the description.

## Multi-level nesting

When a Markdown project file **embeds** other project files or patches,
**every level** must carry its own markers. There is no limit on nesting depth.

The rule applies recursively: if a file written to disk contains code blocks
that represent other files, those inner blocks must also have headings and
markers — because they will be extracted and written to disk too.

### Nesting depth and fence sizing

Each nesting level requires a longer outer fence:

| Level | Role | Fence length |
|---|---|---|
| 0 (outermost) | Your Markdown output | longest |
| 1 | Markdown document being written to disk | shorter |
| 2 | Code file embedded inside that document | shorter still |
| 3 | Code block inside an embedded Markdown | even shorter |

**Rule**: at every level, the enclosing fence is strictly longer than any
fence it contains. Count inward from the deepest block and add 1 backtick
per level going outward.

### Example: 3 levels of nesting

Your output (level 0) contains a documentation file (level 1) that embeds
two project files (level 2):

### `docs/architecture.md`

<!-- file: docs/architecture.md -->
````markdown
# Architecture

### `src/app.py`

<!-- file: src/app.py -->
```python
def main():
    pass
```

### `src/utils.py`

<!-- file: src/utils.py -->
```python
def helper():
    pass
```
````

Here the outer fence is 5 backticks (level 0→1 boundary), inner fences are
3 backticks (level 1→2 boundary). Every block at every level has its own
`<!-- file: -->` marker.

### Example: 4 levels (Markdown embedding Markdown embedding code)

### `docs/meta.md`

<!-- file: docs/meta.md -->
`````markdown
# Meta Document

This document describes another document.

### `docs/guide.md`

<!-- file: docs/guide.md -->
````markdown
# Guide

### `src/example.py`

<!-- file: src/example.py -->
```python
print("hello")
```
````
`````

Fence lengths: 5 → 4 → 3. Each level is strictly shorter going inward.

### Example: patch inside a Markdown document

### `docs/changelog.md`

<!-- file: docs/changelog.md -->
````markdown
# Changelog

The following patch was applied to the config:

### `config/settings.json`

<!-- patch: config/settings.json -->
```diff
--- a/config/settings.json
+++ b/config/settings.json
@@ -1,3 +1,4 @@
 {
-  "debug": false
+  "debug": false,
+  "verbose": true
 }
```
````

## Preservation rules

When you translate, rewrite, refactor, or reformat a document that
contains `<!-- file: ... -->` or `<!-- patch: ... -->` markers:

- **Every marker MUST be preserved in the output exactly as-is**
  (path unchanged, syntax unchanged, `file`/`patch` type unchanged).
- If the source document is missing markers that should be present
  (per the rules above), **add them**.
- If you are producing a new file that embeds code blocks representing
  project files, **add markers** even if the user's prompt did not
  mention them — the rule applies unconditionally.
- **Never silently drop a marker.** If you believe a marker is wrong,
  keep it and add a comment explaining the concern.

## Key examples

### Ordinary project file

### `src/main.py`

<!-- file: src/main.py -->
```python
print("hello")
```

### Patch to an existing file

### `src/main.py`

Add greeting function.

<!-- patch: src/main.py -->
```diff
--- a/src/main.py
+++ b/src/main.py
@@ -1 +1,5 @@
-print("hello")
+def greet(name: str) -> str:
+    return f"Hello, {name}!"
+
+
+print(greet("world"))
```

### Markdown file containing fenced code

### `docs/README.md`

<!-- file: docs/README.md -->
````markdown
# README

```bash
echo "hello"
```
````

### ❌ Wrong — blank line between marker and fence

````markdown
<!-- file: src/main.py -->

​```python
print("hello")
​```
````

✅ Correct — marker immediately before fence:

````markdown
<!-- file: src/main.py -->
​```python
print("hello")
​```
````

### ❌ Wrong — description in heading

````markdown
### `src/main.py` — entry point
````

✅ Correct — description on a separate line:

````markdown
### `src/main.py`

Entry point.
````

### ❌ Wrong — marker dropped during translation

If the source had:

````markdown
### `src/main.py`

<!-- file: src/main.py -->
​```python
print("hello")
​```
````

Then the translated output MUST also have:

````markdown
### `src/main.py`

<!-- file: src/main.py -->
​```python
print("hello")
​```
````

Never produce this (marker missing):

````markdown
### `src/main.py`

​```python
print("hello")
​```
````

### ❌ Wrong — using `<!-- file: -->` for a diff

````markdown
<!-- file: src/main.py -->
​```diff
--- a/src/main.py
...
​```
````

✅ Correct — use `<!-- patch: -->` for diffs:

````markdown
<!-- patch: src/main.py -->
​```diff
--- a/src/main.py
...
​```
````

## Compliance checklist

Before outputting every code block, verify:

1. Does this block represent a file to be written to disk or a patch to apply?
2. Can I name its project-relative path?
3. Is it a full file (`<!-- file: -->`) or a partial update (`<!-- patch: -->`)?
4. Is there a `### \`path\`` heading above it?
5. Is there the correct marker **immediately** before the fence?
6. Do the heading and marker paths match exactly?
7. Is the outer fence longer than any inner fence?
8. If this is a nested document — do inner blocks also have their own markers?
9. If this is a translation/rewrite — did I preserve all markers from the source?
10. If the source was missing markers — did I add them?

If (1) or (2) is *no* → omit heading and marker (illustrative snippet).
If (3)–(10) is *no* → fix before outputting.
