# Rule: File Output Format

When outputting project files, follow ALL of these rules:

## 1. Structure per file

Every project file in your output must have three elements in this order:

1. **Heading** with the file path in inline code
2. **Marker** for automated extraction
3. **Fenced code block** with a language tag

Raw Markdown:

```text
### `path/to/file.ext`

Optional description or notes.

<!-- file: path/to/file.ext -->
​```lang
content
​```
```

How it renders:

- The heading (`### \`path/to/file.ext\``) provides human-readable navigation.
- The HTML marker (`<!-- file: path -->`) enables automated extraction.
- The fenced code block contains the file content.

### Heading format

The heading **must** be a level-3 Markdown heading containing the file path
wrapped in backticks and nothing else:

```text
### `src/main.py`
```

Do **not** add descriptions or suffixes to the heading:

```text
### `src/main.py` — entry point        ← WRONG
### `src/main.py (entry point)`         ← WRONG
### Entry point: `src/main.py`          ← WRONG
```

Place any description as plain text **between** the heading and the marker.

### Marker format

The marker is an HTML comment with this exact structure:

```text
<!-- file: path/to/file.ext -->
```

Format rules:
- Starts with `<!-- file:` (exactly one space after the colon)
- Ends with ` -->` (exactly one space before `-->`)
- Contains a single relative path with no leading/trailing whitespace
- Must be on its own line, **immediately before** the opening fence (no blank
  line between them)
- Only HTML comment syntax — no alternatives (`// file:`, `# file:`, etc.)

Valid:
```text
<!-- file: src/main.py -->
```

Invalid:
```text
<!-- file:src/main.py -->          ← missing space after colon
<!-- file: src/main.py-->          ← missing space before -->
<!--file: src/main.py -->          ← missing space after <!--
<!-- file:  src/main.py -->        ← double space after colon
```

### Heading vs marker: priority and consistency

The path appears in both the heading and the marker. They **must** match
exactly.

- The **marker is authoritative**: the extractor uses it to determine the
  output file path.
- The heading **must agree** with the marker so a human reader is never
  misled.
- If you encounter an existing file where the heading and marker diverge,
  **update the heading** to match the marker.

### Code blocks without markers

Code blocks **without** a `<!-- file: -->` marker are treated as illustrative
snippets and will be ignored by the extractor. To make intent clear to human
readers, **always precede illustrative snippets with explanatory text**:

Good — intent is clear:

```text
Example of a curl request:

​```bash
curl https://example.com
​```
```

Ambiguous — reader may wonder if this is a project file:

```text
​```bash
curl https://example.com
​```
```

## 2. When to apply this rule

This rule applies whenever you output content of a file **for which the path
is known** — regardless of where that content appears:

| Situation | Apply rule? |
|---|---|
| Outputting a project file in your response | **Yes** |
| Embedding a project file inside a Markdown file that is itself part of your output | **Yes** (recursive) |
| Showing an illustrative snippet (no real file path) | No — omit the marker |

**Decision criterion:** if you can name a concrete file path within the
project structure for a code block, it is a project file — use the full
heading + marker structure. If the code block exists only to explain a
concept, demonstrate a command, or show example output, it is illustrative —
omit the marker.

This decision is made by you (the LLM) based on the conversation context.
When genuinely uncertain, **ask the user**.

## 3. Markdown file content (or any content containing triple backticks)

When the file itself contains triple backticks (e.g. `.md` files with fenced
code blocks), wrap the entire block in **quadruple** backticks so the inner
fences render correctly:

### `docs/README.md`

<!-- file: docs/README.md -->
````markdown
# Title

Some text

```bash
echo "hello"
```
````

## 4. Markers inside Markdown project files

When a Markdown project file **itself contains code blocks that represent
project files** (e.g. a design document showing file contents), those inner
code blocks **must also carry `<!-- file: -->` markers**.

The markers are part of the file's content — they will be written into the
Markdown file on disk so that the same extractor can process it recursively.

**When to include inner markers:**

A Markdown project file is any `.md` file that is itself output as a project
file (i.e. it has its own heading and marker in your response). If such a
file contains code blocks with `### \`path\`` headings, those code blocks
**must** have markers — they represent real project files that the extractor
should be able to extract recursively.

**Example — a design doc that embeds two project files:**

### `docs/architecture.md`

<!-- file: docs/architecture.md -->
`````markdown
# Architecture

## Entry point

### `src/main.py`

<!-- file: src/main.py -->
```python
print("hello")
```

### `src/utils.py`

<!-- file: src/utils.py -->
```python
def helper():
    pass
```
`````

Note: the outer fence uses **quintuple** backticks because the content
already contains quadruple backticks (or triple). Always use a fence that is
at least one backtick longer than the longest fence inside the content.

### When to omit inner markers

Omit `<!-- file: -->` inside a Markdown project file **only** when a code
block is truly illustrative (e.g. a shell session example, a snippet that
does not correspond to any real file). If the code block has a
`### \`path/to/file\`` heading above it, it **must** have the marker.

### Descriptions between heading and code block

You **may** place descriptive text — including illustrative code blocks —
between the heading and the marker. The extractor will ignore any code block
that lacks a `<!-- file: -->` marker, so there is no ambiguity:

### `src/main.py`

This replaces the old approach:

```python
# old code — illustrative only, no marker
```

<!-- file: src/main.py -->
```python
# new code — this will be extracted
```

## 5. Multiple files

Output files sequentially, each with its own heading and marker:

### `src/main.py`

Entry point.

<!-- file: src/main.py -->
```python
print("hello")
```

### `src/utils.py`

<!-- file: src/utils.py -->
```python
def helper():
    pass
```

## 6. File paths

All paths are **relative to the project root**. Never use absolute system
paths (`/etc/...`, `/usr/...`) as the marker path.

If a file is ultimately destined for an absolute location on a target system
(e.g. inside a Docker container, deployed via Ansible), store it locally
under a project-relative path that reflects its purpose (e.g.
`deploy/nginx/nginx.conf`) and document the real target path in a comment or
description. The project directory is the single source of truth.

## 7. Fence length rules

| Content contains       | Outer fence length |
|------------------------|--------------------|
| No backtick fences     | 3 (triple)         |
| Triple backtick fences | 4 (quadruple)      |
| Quadruple fences       | 5 (quintuple)      |
| *N*-length fences      | *N + 1* or more    |

Always inspect the content and pick a fence length that is **strictly
longer** than any fence inside.

## 8. Common mistakes

### ❌ Missing marker

```text
### `src/main.py`

​```python
print("hello")
​```
```

The extractor will **skip** this block entirely. Always add the marker:

```text
### `src/main.py`

<!-- file: src/main.py -->
​```python
print("hello")
​```
```

### ❌ Marker not immediately before the fence

```text
### `src/main.py`

<!-- file: src/main.py -->

​```python
print("hello")
​```
```

The blank line between the marker and the fence **breaks extraction**.
The marker must be on the line **immediately preceding** the opening fence:

```text
### `src/main.py`

<!-- file: src/main.py -->
​```python
print("hello")
​```
```

### ❌ Heading and marker paths diverge

```text
### `src/main.py`

<!-- file: src/app.py -->
​```python
print("hello")
​```
```

A human reads `src/main.py`; the extractor writes `src/app.py`. Fix the
heading to match the marker:

```text
### `src/app.py`

<!-- file: src/app.py -->
​```python
print("hello")
​```
```

### ❌ Description in heading

```text
### `src/main.py` — entry point

<!-- file: src/main.py -->
​```python
print("hello")
​```
```

The heading must contain only the path. Move the description below:

```text
### `src/main.py`

Entry point.

<!-- file: src/main.py -->
​```python
print("hello")
​```
```

### ❌ Wrong fence depth for nested Markdown

`````text
### `docs/README.md`

<!-- file: docs/README.md -->
```markdown
# Title

​```bash
echo "hello"
​```
```
`````

The inner fence closes the outer fence prematurely. Use **quadruple**
backticks for the outer fence:

``````text
### `docs/README.md`

<!-- file: docs/README.md -->
````markdown
# Title

```bash
echo "hello"
```
````
``````

### ❌ Absolute path in marker

```text
### `/etc/nginx/nginx.conf`

<!-- file: /etc/nginx/nginx.conf -->
​```nginx
server { ... }
​```
```

Use a project-relative path:

```text
### `deploy/nginx/nginx.conf`

<!-- file: deploy/nginx/nginx.conf -->
​```nginx
server { ... }
​```
```

### ❌ Marker on an illustrative snippet

```text
Here's how `curl` works:

<!-- file: ??? -->
​```bash
curl https://example.com
​```
```

Illustrative snippets have no file path. Omit both the heading and the
marker, and precede with explanatory text:

```text
Here's how `curl` works:

​```bash
curl https://example.com
​```
```

### ❌ Missing inner markers in Markdown project file

`````text
### `docs/setup.md`

<!-- file: docs/setup.md -->
```markdown
# Setup

### `scripts/install.sh`

​```bash
#!/usr/bin/env bash
echo "installing"
​```
```
`````

The inner code block represents a real project file but has no marker.
The extractor cannot extract `scripts/install.sh` recursively. Add it:

``````text
### `docs/setup.md`

<!-- file: docs/setup.md -->
`````markdown
# Setup

### `scripts/install.sh`

<!-- file: scripts/install.sh -->
```bash
#!/usr/bin/env bash
echo "installing"
```
`````
``````

### ❌ Invalid marker format

```text
<!-- file:src/main.py -->          ← missing space after colon
<!-- file: src/main.py-->          ← missing space before -->
<!--file: src/main.py -->          ← missing space after <!--
```

Correct format:

```text
<!-- file: src/main.py -->
```

## 9. Summary

| Element | Required? | Purpose |
|---|---|---|
| `### \`path\`` heading | Yes | Human readability, navigation |
| Heading contains only the path | Yes | No descriptions in heading line |
| `<!-- file: path -->` marker | Yes | Automated file extraction |
| Heading ↔ marker path match | Yes | Prevent human/machine mismatch |
| Marker immediately before fence | Yes | Extractor relies on adjacency |
| Marker format: `<!-- file: path -->` | Yes | Consistent parsing |
| Language tag on fence | Yes | Syntax highlighting |
| Description between heading and code | Optional | Context for the reader |
| Explanatory text before illustrative snippets | Recommended | Clarify intent for human readers |
| Markers inside Markdown content | Yes, for project-file code blocks | Recursive extraction |
| Correct fence length | Yes | Proper rendering of nested fences |
| Relative paths only | Yes | Project dir is source of truth |
